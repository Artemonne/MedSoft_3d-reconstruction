# 02. Архитектура и ключевые решения

## Стек

- Python 3.12 (фиксировать проверенную конфигурацию и версии зависимостей после первых запусков).
- PySide6: GUI.
- pydicom 3.x: DICOM-метаданные, пиксели, Modality LUT.
- NumPy + SciPy: хранилище HU-объёма, фильтры, операции с массивом.
- scikit-image: проверенная реализация `measure.marching_cubes`.
- PyVista + pyvistaqt + VTK: Qt 3D-виджет, повороты, отображение треугольной сетки, обработка и экспорт.
- pytest: тестирование; необязательно ruff для стиля.

Стек документарно реализуем на Windows x64 / CPython 3.12: на 24.11.2026 проверены Requires-Python и подходящие wheels основных пакетов в PyPI. Версии-кандидаты и границы проверки приведены в `06_stage0_audit.md`; совместная установка и OpenGL ещё не проверены. Не считать версии `latest` проверенной конфигурацией. В начале этапа 1 создать чистый venv, настроить `QT_API=pyside6` до импорта QtPy/pyvistaqt, установить и зафиксировать совместимые версии, выполнить `pip check` и ручной запуск QtInteractor. Использовать один QApplication, без второго event loop и без обязательного BackgroundPlotter.

Основной профиль: классический однокадровый CT, Implicit/Explicit VR Little Endian, Explicit VR Big Endian, Deflated Explicit VR и RLE при подтверждённом декодировании. Для JPEG/JPEG-LS/JPEG 2000 нужен документированный профиль декодеров pydicom: `pylibjpeg` с нужными плагинами и/или `pyjpegls`, только с проверкой соответствующей transfer syntax. Это обоснованные дополнительные зависимости для чтения распространённых CT; не добавлять все декодеры без проверки необходимости. Неподдерживаемое сжатие распознавать до построения объёма. Enhanced CT/multi-frame и нерегулярные/сдвинутые стеки пока ограничены; это сохраняет риск проверки R10 на неизвестных файлах преподавателя.

Почему не React/TypeScript: это не требуется, а Python-библиотеки дают уже отлаженные методы DICOM и 3D. Почему не 3D Slicer как база: лекция перечисляет готовые платформы, но лабораторная требует разработать **собственное простое приложение**; использовать Slicer как внешний инструмент проверки экспортов можно при желании, но не подменять им реализацию.

## Поток данных

```text
Выбор файлов (GUI)
  → DICOM loader: валидность, группировка по series UID
  → Geometry: порядок/ориентации/spacing/совместимость
  → HU: декодирование + Modality LUT для каждого кадра/среза
  → CTVolume: ndarray[z,y,x] + геометрия + метаинформация
  → CTVolume + valid_voxels → Threshold ИЛИ RegionGrowing → boolean mask[z,y,x]
      → этап 1: volume rendering бинарной маски → QtInteractor
      → этап 2: Marching Cubes → исходный Mesh в LPS, мм → QtInteractor
          → этап 3: Smoothing / Decimation / Repair → активный Mesh → QtInteractor
          → STL из актуального активного Mesh
```

## Контракты между модулями

- `CTVolume`: `data_hu` float32 `[z,y,x]`, `valid_voxels` boolean той же формы, `spacing_mm=(dz,dr,dc)`, `origin_lps_mm=P0`, направления `u,v,n`, метаданные, UID серии/FrameOfReference и версия объёма. Преобразование в float32 проверять на HU-тестах; не округлять до целых.
- `Segmentation`: бинарная `mask[z,y,x]` той же формы; метод, параметры, seed, версия исходного объёма и собственная версия. `mask` всегда является подмножеством `valid_voxels`.
- `Mesh`: обычные массивы вершин LPS в мм и индексов треугольников, метрики, версия маски и операции обработки. Отдельно неизменённая исходная и активная сетки; Qt/PyVista-объекты сцены не входят в модель.
- Не привязывать `dicom_loader.py` и алгоритмы к PySide6.

## Геометрия: главное место возможных ошибок

1. В DICOM `PixelSpacing = [расстояние между строками (rows), расстояние между столбцами (columns)]`, мм.
2. `ImageOrientationPatient` задаёт два направления в плоскости; направление срезов — их векторное произведение.
3. Для сортировки использовать проекцию `ImagePositionPatient` на нормаль, а не `SliceLocation`, `InstanceNumber` или имя файла по умолчанию.
4. Разность координат соседних срезов по нормали определяет фактический шаг. Дубли и неравномерный шаг нельзя тихо игнорировать.
5. В `marching_cubes` массив `[z,y,x]`, следовательно `spacing` там задаётся в порядке `[slice_spacing, row_spacing, col_spacing]`, а возвращаемые вершины должны быть преобразованы в выбранную систему координат просмотра/экспорта. При необходимости применить DICOM orientation и origin.
6. Сырой pixel_array — ещё **не** HU. Для CT применить Modality LUT / slope/intercept. VOI LUT/windowing не использовать для численной сегментации.
7. Следить за неправильным отражением/перестановкой осей, особенно после трансформации и экспорта.

### Единый договор о координатах

Использовать DICOM LPS для человеческих CT (x влево, y кзади, z к голове), мм. Обозначения: `u=IOP[0:3]` — направление при увеличении индекса столбца x; `v=IOP[3:6]` — направление при увеличении строки y; `n=u×v`; `dr,dc=PixelSpacing`. После сортировки проекций `dot(IPP,n)` по возрастанию `dz>0`, `P0` — IPP первого среза (центр первого пикселя). Для регулярного ортогонального стека:

`P(z,y,x) = P0 + z*dz*n + y*dr*v + x*dc*u`.

Проверять ортонормальность IOP, положительные spacing, единые Rows/Columns/PixelSpacing, SeriesInstanceUID, StudyInstanceUID и FrameOfReferenceUID. Разные FrameOfReference разделять, даже внутри одной серии. Проверять `IPP[k] ≈ P0 + k*dz*n`: только равенства расстояний по нормали недостаточно при боковом сдвиге. Предлагаемые инженерные допуски: норма/ортогональность IOP 1e-4; изменение направления 0.01 градуса; отклонение шага `max(0.01 мм, 0.001*dz)`; невязка полной позиции 0.05 мм. Зафиксировать их тестами на границах допуска, а не менять под конкретный набор. При невыполнении — понятный отказ; интерполяцию в первой версии не делать.

Для базового volume rendering точки ImageData соответствуют центрам вокселей: dimensions `(nx,ny,nz)`, spacing `(dc,dr,dz)`, origin `P0`, направления столбцов матрицы `(u,v,n)`. Развёртка массива `[z,y,x]` должна давать x как самый быстрый индекс VTK. Проверить это на асимметричном объекте; поворот камеры не исправляет ошибку осей. Отрисовывать бинарные значения с прозрачностью 0 для фона и nearest-интерполяцией, без изменения исходной маски. Визуализацию проверять и для полной маски с известным внешним фоном.

Для Marching Cubes возвращаемый порядок вершин `(z_mm,y_mm,x_mm)` согласован с `spacing=(dz,dr,dc)`. После одного слоя нулевого padding вычесть `(dz,dr,dc)` из этих вершин, затем применить только направления и P0: масштаб второй раз не умножать. Полученный mesh хранить в LPS. Проверять ориентацию треугольников/наружных нормалей после перестановки осей; нормали из индексной системы нельзя без проверки перенести в LPS. Padding закрывает обрезанную границу предположением о внешнем фоне и не восстанавливает отсутствующую анатомию; это отдельно от mesh repair.

## Реконструкция и качество изображения

- Этап 1 закрывает обязательную часть независимо от дополнительных методов: **volume rendering бинарной маски**. На этапе 2 добавить переключение «Маска / Поверхность Marching Cubes» и явно показывать текущий режим. Это устраняет зависимость базового сценария от ещё не реализованного этапа.
- Threshold: бинарная маска `volume_hu >= threshold_hu`, без неявного сглаживания или морфологии, чтобы тесты были воспроизводимыми.
- Region Growing: 6-связный обход из seed, переход p -> q при `abs(HU(q)-HU(p)) <= tolerance_HU` и валидности q; точный критерий — `01_requirements.md`, C3. Начинать только с валидного seed, проверять границы, не строить глобальную маску вместо наращивания. Метка visited, компактный фронт обхода, прогресс и отмена нужны для больших областей; не обещать мгновенный Python-обход десятков миллионов вокселей. Проверить протекание на плавном градиенте и остановку на резкой границе.
- Marching Cubes: `skimage.measure.marching_cubes` на binary volume с `level=0.5` и физическим spacing; для mask касающейся границы объёма предусмотреть padding для корректной замкнутой поверхности.
- Postprocessing: smooth (например, Laplacian), decimate с контролем целевой доли и сохранения геометрии, repair открытых границ/малых дыр и несвязных компонентов с валидацией. Не обещать автоматический успешный repair любой повреждённой поверхности.

Конкретизация без новых библиотек: `PolyData.smooth` (Laplacian), `decimate_pro` на треугольной сетке (`reduction` означает долю удаляемых треугольников; сохранение топологии может ограничить достижимую долю), ремонт малых отверстий и явно выбранных лишних компонентов. `fill_holes` использует радиус ограничивающей сферы отверстия, а не его площадь. Официальная документация предупреждает о segfault: если выбран этот фильтр, выполнять его в отдельном локальном процессе `multiprocessing` со spawn, тайм-аутом и проверкой кода завершения, передавая только массивы сетки. Обычный try/except и QThread не защищают приложение от native crash. Не вводить другой repair-пакет без проверки API, Windows wheels и необходимости.

После каждой операции: конечные координаты, валидные треугольники, число граней, boundary/non-manifold edges, компоненты, bounds; для закрытой сетки также объём. Сравнивать форму с исходной, показывать до/после и иметь сброс. Если дефектов нет, «Исправлений не требуется» допустимо; зачёт repair подтверждать отдельным воспроизводимым дефектом. Не удалять малые компоненты автоматически только по размеру: они могут быть анатомией. Политику удаления и размер отверстий выбирает пользователь.

STL хранит только геометрию: в README указать мм и LPS, без скрытого центрирования/перемасштабирования. Камера и экранные actor transforms не меняют экспортируемый mesh. Экспорт доступен в режиме актуальной поверхности; сначала зафиксировать её на экране, затем сохранить те же вершины/грани. Повторное чтение через VTK проверяет round-trip, а независимая проверка — открытие в стороннем редакторе. OBJ не нужен для максимума баллов.

## GUI

Левая часть: загрузить файлы / серия, метаданные, расстояния; режим сегментации; HU/seed/tolerance; кнопки методов и параметры обработки. Центр/справа: 3D QtInteractor с мышью; дополнительная 2D-панель исходного среза с навигацией по Z и click-to-seed (важно для +5 баллов). Внизу: статус, прогресс, ошибки; при обработке отключить несовместимые действия.

Изменение порога не должно подвешивать GUI. Можно обновлять с debounce, показывать статус и отменять прошлую задачу. Работа с Qt/VTK GUI — только в GUI-потоке.

Сцену, actors, renderer и общие VTK-объекты изменять только в GUI-потоке. NumPy/scikit-image и изолированные экземпляры VTK-фильтров могут вычисляться в worker без доступа к сцене; передавать готовые массивы по сигналам. Worker-object переносить в QThread; результат принимать только при совпадении версии входных данных и параметров. При новых HU/seed/tolerance сбрасывать зависимые mesh и обработку, блокировать экспорт до актуального результата. Непрерываемый нативный фильтр можно дождаться с отбрасыванием устаревшего результата; не обещать немедленную отмену любой библиотеки. Repair с риском native crash — отдельный процесс, управляемый worker. При закрытии окна корректно завершать задачи и QtInteractor.

Не запускать неограниченное число расчётов на каждое движение слайдера: одна активная тяжёлая задача и только последний ожидающий запрос. В локальном Region Growing отклонение q при проверке ребра p -> q не означает окончательного запрета q: другой принятый сосед может дать допустимый переход. Результат не должен зависеть от порядка обхода соседей.

## Данные, хранение, производительность

- Файлы загружаются и обрабатываются локально. Не хранить/пересылать реальные PatientName/PatientID в логах/внешних сервисах.
- Системы с 32 ГБ RAM достаточно для многих КТ-серий, но объём может быть большим: `512×512×300` ~78,6 млн вокселей; в float32 ~315 МБ, в float64 ~629 МБ, без копий/сетки/GUI. Не создавать ненужные массивы.
- Для отладки использовать синтетический DICOM и публичные **обезличенные** исследования. Не коммитить чужие медицинские данные.
- Требование PDF — произвольная серия КТ на файлах преподавателя. Граница первой реализации (classic CT, регулярная геометрия, проверенные transfer syntaxes) не ослабляет это требование: отказ на валидном неподдерживаемом CT остаётся риском R10. Перед защитой получить максимально разнообразные независимые серии; при обнаружении нужного формата расширить поддержку и проверки до финальной приёмки.
